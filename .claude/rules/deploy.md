## Production safety

Production is the auth server's host, which this app shares. On 2026-09-28 a `sed` range in an auth repository task ran part of that repository's `PRODUCTION.md` as bash on the server, prose included, since the backticks of inline code turn prose into command substitutions. Among other things it reinstalled, removed and reinstalled this app's site file (see [change_log.mdx](change_log.mdx) and the auth repository's `change_log.mdx`, D4-IR). Rules for every task:

- Never run text extracted from a document or file on a server: no `sed`, `awk` or `grep` output, and no variable filled from a file. Check a documented command by reading it, or by running it in a throwaway local container. This applies to every command the agent runs and every command it writes into a deploy checklist, where commits are named explicitly. The runbook's generic blocks for the human operator ("Update the app", "Roll an update back") may read `/root/finance-tracker.previous`; they print the commit they read before they use it.
- Write every server command out explicitly on the command line. Never pipe a file or a heredoc into a remote shell (`ssh host bash -s < file`, `ssh host 'bash -s' <<'EOF'`, `… | ssh host bash`).
- The one exception is the deploy scripts (OPS-1): `deploy/deploy.sh` and `deploy/rollback.sh`, with `deploy/common.sh`, are committed, reviewed and tested (`deploy/tests/`), and the operator runs them on the server as files, from its clone. They run SQL only from the committed check files `deploy/checks/*.sql` (and the role's own description, `ROLE_SQL` in `deploy/common.sh`), through `psql` as the read-only database role `finance_checks` (since F6b: no superuser, a member of `pg_read_all_data` only, `default_transaction_read_only = on` set on the role, no password; created once by the runbook's command, "A read-only role for the deploy checks"), with `PGOPTIONS=-c default_transaction_read_only=on` as well; they stop when the role is missing, is a superuser or may write to a table of `app`, and refuse a check file that holds a backslash, so `psql` runs no meta-command from it. Their state files (`/var/lib/finance-deploy`) are data, parsed and never sourced; `rollback.sh` takes its commit from the operator and only compares it with the record. Nothing else in this rule changes. Decided after OPS-1's review (2026-10-02, by the PM) and built in F6b: the exception stays, with read-only a property of that role; a cancelled CI run refuses the deploy; a stop the owner judges harmless and a manual deploy are closed with `deploy/deploy.sh adopt`, which records the running revision as the last good deploy and touches no git, image, container or database.
- Never run a runbook section that changes state (restore, rotate, delete, update) as a test. It runs only when the task is to do exactly that.
- Production is read-only by default, unless the task says otherwise.

## Deploy checklists

Since OPS-1 a stage deploys with `deploy/deploy.sh` ([deploy/RUNBOOK.md](deploy/RUNBOOK.md), "Deploying with deploy.sh"). A batch's deploy checklist (D-879: since BATCH-1 several stages are deployed together, once; the "stage" below is the batch's name, `BATCH-1`), in the report of the batch's last stage:

1. Names the commit, in full, and the batch (it is on `origin/main` already, D-878; nothing to merge or push): `cd /opt/finance-tracker && deploy/deploy.sh run <commit> <stage>`, and what its steps should print (the commits, the migrations, the files under `deploy/`, the Flyway line).
2. Comes with the batch's `deploy/checks/<batch>.sql` and `<batch>.expected` in the commit, covering every stage of the batch (a batch holds at most one migration, D-879): read-only SQL without a backslash, whose output stays the same from day to day (no times), tried on a throwaway database migrated by Flyway to the batch's migration (a database restored from a dump renders some constraints differently).
3. Updates `deploy/checks/numbers.sql` when a migration adds a table: a key per table, sorted (it takes effect from the next deploy).
4. Replaces the browser checks and the smoke test with the end-to-end suite (QA-1, D-51): on the laptop, from a clean checkout of the deployed commit, `cd e2e && E2E_FAMILY=<on|off> npm run e2e:prod` (the switch's position after the deploy), whose summary the owner pastes; then `deploy/deploy.sh finish`, whose two questions (the browser checks, the smoke test) are answered `yes` only if every spec of that summary passed and its cleanup deleted both accounts' data, and says where `finish` appears that it comes only after the suite. Anything the stage's agent couldn't automate is listed after the suite, each with the reason, and only that is checked by hand, before `finish`. (D-588, since UX-13-doc) Right after the suite's block (the checklist's step 5) every checklist carries, in its own words: "If any spec fails, or the cleanup does: don't run the suite again and don't run `finish`; send the whole summary to the PM, who decides (D-58, D-59)." It replaces "D-58 and D-59 apply as in D4b's checklist" for later checklists; earlier checklists stay as they are (UX-13's run 2 and `finish` came before the PM had read run 1's failed summary).
5. Puts the rollback command last, in a block of its own, whose first comment says it is only for a failed deploy: `deploy/rollback.sh <the last good commit>`.

Since BATCH-1 (D-867, D-868, D-878) every stage is committed on `main` and the owner pushes it right after the agent's report, before the PM's review; `feature/family-budget` stays on GitHub as it was, no longer pushed, and `ci.yml` runs on pushes to `main` only. Stages are deployed in batches (several stages, one checklist, one deploy, at most one migration, D-879), with no "-doc" stage: a batch's deploy is recorded in the first commit of the next batch. Up to then merges into `main` were fast-forwards made on the laptop, as the checklists said (D-57), so that a checklist could name the commit to deploy before the deploy; no pull request is merged on GitHub with a merge commit. PR #13's merge commit `8d75f83` stays (no force-push, no revert), and OPS-2b deployed it (2026-10-05).

The template (D-127, since F8f), on top of the numbered rules:

- A step 0 before step 1, read only, on the laptop: `git fetch origin`; HEAD's full hash and subject (on `main`); `origin/main`'s hash; `git --no-pager log --oneline <production's commit>..origin/main`, whose lines are printed by git and never counted in the checklist's prose (OPS-5's step A0 said three commits and git printed four: say "the commits git prints" and let the PM compare them with the report); `git merge-base --is-ancestor <M> origin/main` printing `PUSHED` or `NOT-PUSHED`; `git status --porcelain`. (Since BATCH-1, D-868, D-878: work is on `main` only and the owner pushes after each report, so M is already on `origin/main`; step 1 checks that and CI on M, once on `main`, with no merge. Before it, step 0 compared `origin/main` with `feature/family-budget`.)
- Every laptop git command that can page runs as `git --no-pager`.
- A dirty tree stops a chain: `test -z "$(git status --porcelain)"`, never `git status --short`.
- CI on M is checked by two read-only blocks: the runs with their jobs (`actions/runs?head_sha=M`, then each run's jobs), and the check runs.
- The server pre-flight prints `/run/systemd/shutdown/scheduled` (`cat … 2>&1`), and a scheduled reboot stops the deploy (D-126); no step runs between 03:30 and 04:30 UTC, when the host may reboot by itself (D-125), but the rollback of a site that is down.
- Step 9 has a read-only block listing the "CI on Ubuntu 26.04" runs for M (`actions/workflows/ci-ubuntu-26.yml/runs?head_sha=M`) with event, branch, attempt, status, conclusion and each job.
- (D-519, since UX-11) The pre-flight prints the running images in full. A checklist's expected Flyway line in the api's log is the one that container's own start printed: `Successfully applied … migration` only when that start applied it, otherwise `Schema "app" is up to date. No migration necessary.` (UX-10's checklist expected the latter from UX-9's container, which had applied V17). (D-711, since UX-17-doc) Where a checklist expects an image's `:latest` to be the running image, it allows an image of the same content after a build from cache (UX-16's 3.3 built the api from cache into `1a4aab56…`, which `:latest` named while the container stayed on `b3c23c23…`, the same content); the scripts compare by content.
- (D-917, since BATCH-1b) A checklist starts from what production runs, as its pre-flight and `last-good` show it, not from what an earlier report assumed (BATCH-1's was first written over `d9cf51f` while production already ran FX-1); its check file prints no constraint's own text (a restored database renders one differently from a migrated one, D-912): it asks the catalogue what the constraint names or holds, so the same lines come out of both.

- (since HIST-1's first commit) After a DNS change the checklist checks the laptop's own resolver (`resolvectl dns wlp4s0`) before `e2e:prod` (WEB-1's first two suite runs failed in `apex` because the router cached the old records) and says to restore it with `nmcli device reapply wlp4s0`.
- (since OPS-6) A checklist's check of Keycloak's sign-in page asks for it as a client does: the authorization URL carries `code_challenge` and `code_challenge_method=S256`, a verifier generated in the command itself (`v=$(openssl rand -base64 48 | tr -d '=+/' | cut -c1-64)`, `c=$(printf %s "$v" | openssl dgst -sha256 -binary | openssl base64 -A | tr '+/' '-_' | tr -d '=')`), because the client `finance-tracker` requires PKCE and without it the page is an error that a `grep` prints nothing from (OPS-5's step A7 printed nothing).
- (D-965, since OPS-6b) Every commit that a checklist deploys has its own CI run on GitHub: such commits are pushed one at a time, each after the previous one's CI is green (OPS-6's A was pushed with B and had no run, D-960). `deploy.sh run` and `db-image` deploy only `origin/main` (OPS-6's first A1 was refused for that, D-961): a package that deploys two commits pushes the second only after the first's `finish`, and the checklist's step 0 prints `origin/main` and what it must be.
- (D-945, since OPS-6) A checklist that applies a database image (`deploy.sh db-image`) names the forbidden windows itself (03:30Z to 04:30Z, the dumps at about 02:30Z, Hetzner's backup at about 10:49Z), since only a scheduled shutdown is guarded; its pre-flight prints the container's `.Config.Image`, `SELECT version()`, the local postgres images and the index query inline; its last block, alone, is the rollback, whose first comment says it is only for a failed upgrade (D-946).
- (D-942, since OPS-5) A read-only `apt list --upgradable` in a checklist ends with `| cat` (apt 3 opens a pager); `pg-restore-test finance` or `auth` is preceded by a fresh dump (`systemctl start pg-backup@finance.service`, `@auth.service`, its `last-success` checked), since the test compares the newest dump with a production that has changed since (OPS-4's step 12 failed that way). (D-941) A checklist expects the 24 numbers its own pre-flight printed; `verify` compares them with the latest run's and prints the differences as information, never a stop.

Every checklist states at its top the commit, the stage and the expected state of the family switch, and is used only for that deploy (2026-10-04's empty run re-ran F7b's checklist by mistake). Every `run` is preceded by a read-only pre-flight block on the server (Docker's version and image store, `last-good`, the last lines of `history`, the running containers' image IDs and content identities), whose output the PM sees before the deploy goes on (OPS-2).

Every block starts with `# On the laptop` or `# On the server`. Since OPS-2b a server block can't run on the laptop (2026-10-04: OPS-2's pre-flight, pasted on the laptop first, failed at its `cd` and read the laptop with the rest): a one-line server block starts with `cd /opt/finance-tracker &&`, and a multi-line one is wrapped as `cd /opt/finance-tracker && {` on its first line and `}` on its last, so that pasted on the laptop, where that folder doesn't exist, none of it runs. Since D-330 a laptop block can't run on the server either (2026-11-05: UX-1's read-only "CI on Ubuntu 26.04" block ran on the server first, harmlessly): a one-line laptop block starts with `cd ~/dev/finance-tracker &&` (or another folder that exists only on the laptop, such as `~/dev/finance-tracker/e2e`), and a multi-line one is wrapped as `cd ~/dev/finance-tracker && {` on its first line and `}` on its last (D-334), so that pasted on the server none of it runs. Image tags are written as the scripts name them: `finance-tracker-api:<the full commit hash>`, never 7 characters (OPS-2's checklist inspected `:4510003`, which names no image). The manual workflow "CI on Ubuntu 26.04" is never started between a push and that commit's `run`: up to OPS-3 `deploy.sh`'s gate counted every check run of the commit (D-44); since OPS-3 it counts only those of `ci.yml`'s runs (D-280), and the rule stays. The next block is pasted only once the shell prompt (`root@auth-1:…#`) has returned (OPS-2: on 2026-10-03 two `switch on` took the next pasted block as their answer). Every server command that asks a question (`deploy.sh run`, `finish`, `adopt`, `rollback.sh`) stands alone in its block, and its answer is typed at the terminal, never pasted: F6b's `finish` took the next pasted block as its two answers (2026-10-02). A stop judged harmless (after `verify` and the end-to-end suite) and a manual deploy end with `deploy/deploy.sh adopt` instead of `finish`. The manual procedure (the runbook's "Update the app") is only for when the script itself is at fault, and then keeps the earlier rules: the restore test right after a fresh backup, the numbers saved and compared with `diff`, the expected commits named.
