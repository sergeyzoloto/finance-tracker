  - `POST /api/family-ledgers/{ledgerId}/settlements` (new, only with the switch on; 201): `date`,
    `amount`, `payerMemberId`, `payeeMemberId`, `comment`, and for the recorder's own side
    `paymentAccountId` or `paymentLater`. The answer is the record (type `SETTLEMENT`, category,
    split method and shares empty) with the new `payee`; settlements are listed, read, changed and
    deleted through `/records` like expenses.
  - Who: a member with an account who pays or receives; an owner, between two members without an
    account ("Only an owner of the family budget records a settlement between two members without an
    account.", 409). A member with an account named by someone else: 422 `PAYER` or `PAYEE` (new
    code); the same member twice: `PAYEE`; a side with an account who joined after the date:
    `JOINED_AFTER`; before the start date: 409.
  - Posting (`FAMILY_SETTLEMENT`, link `SETTLEMENT`): the payer's account −x and debt +x, the
    receiver's account +x and debt −x. The recorder's side on the account they name or their
    placeholder; the other side, with an account, on their "Payments without a specified account",
    which they move to an account through `PATCH /records/{recordId}` (`paymentAccountId`,
    `paymentLater`) or `PATCH /api/entries/{id}/family-payment` (`accountId`, `later`), without a new
    version or a journal line; nothing for a side without an account.
  - Changes: the recorder (between members without an account, its author or an owner) changes the
    date, amount and comment and deletes it, also through their own side's entry; a category, split,
    other payer or note is 422; frozen and stale are 409 ("Settlement 2 has changed since version
    0. …", "The settlement is frozen: …", "Settlement 2 not found."). A change of the date or amount
    moves the other side's part back to their placeholder if they had put it on an account of
    theirs: only its member posts to their own account (D-8).
  - The journal: creation (date, amount, payer, `payee`, comment), changes, deletion; its record
    summary gains `type`. `yourPayment` is each side's own.
  - The posting service posts sides generally (the expense's payment is the payer's side); the
    personal endpoints: `DELETE /api/entries/{id}` of one's own side deletes the settlement if one
    recorded it (else 409 naming the recorder), `PUT` answers 409 ("Entry N is your side of a
    settlement in the family budget "Home"; change it there."). `ledger.FamilyPayments.deleteExpenseOf`
    is now `deleteRecordOf`. The expense messages are unchanged apart from the payment endpoint's
    "Entry N is not your payment for a family expense or your side of a settlement, …".
  - Tests: new `FamilySettlementApiTests` (3); `DataIsolationApiTests.aSettlementSideIsItsMembersOwn`
    (new; the file gained 106 lines and lost none); `FamilyRecordRandomTests` with settlements in the
    mix; `CrossLedgerWriterTests` refuses her cash and a note on her side of a settlement;
    `FamilyInvariants` computes balances with incomes and settlements (topic D's formula) and checks
    that no settlement has shares; `ApiTests` (401 and the OpenAPI paths) and
    `FamilySwitchOffApiTests` (23 endpoints) with the new endpoint.

## 2026-09-28 · One token refresh per session, late login callback (D3a)

Commit `385cd2a`; the deploy's records: `5711645`.

**Changes**
- `SessionAccessTokenFilter`: one request of a session refreshes the access token at a time, which
  fixes the bug D3 found: parallel requests each refreshed an expiring token with the same refresh
  token, Keycloak refused the second with "Maximum allowed refresh token reuse exceeded", and the
  api ended the session.
  - A request whose token expires within the minute takes a `ReentrantLock` kept in the session,
    reads the session's authorized client again under it, and refreshes only if that token is
    still expiring. Otherwise it uses the token that the request before it got.
  - A refused refresh (`invalid_grant`) ends the session only while the refused refresh token is
    still the session's; tokens stored meanwhile by a sign-in in the same session stay. The
    manager's default failure handler, which removed the stored client on `invalid_grant`, is
    replaced by a no-op, so the filter decides alone. The end of a session is logged:
    `Keycloak refused to refresh the session's access token (…), so the session ends`.
  - The lock is in the JVM, which assumes the single api instance; the Javadoc and
    `docs/auth.md` say so.
  - Found on the way: Keycloak 26 (`TokenManager.validateTokenReuseForRefresh`) also detaches the
    client session when a refresh token is reused. The token the first refresh brought would then
    fail at its own refresh, so avoiding the second use matters, not only tolerating its error.
- `SecurityConfig`: a callback that fails with `authorization_request_not_found` in a session that
  already holds tokens goes to `/?login=done`, like a successful login, and logs
  `A late callback of a finished sign-in`. Otherwise the login-failed notice stays. The task said
  to redirect to `/`. `/?login=done` also lands on `/`, and when the browser dropped the first
  callback's response, the frontend reopens the page the user was on.

    subject's refreshes, and can give refreshed access tokens another lifetime than the first.

## 2026-09-22 · Backend: resource server, domain model, REST API

Commit `81f9779`

**Changes**
- Stateless OAuth2 resource server: it checks the token's issuer and signature using the realm's
  JWK Set URI. There are no sessions and no login page. CSRF protection is off, since only bearer
  tokens are used; with it on, a write without a token got 403 instead of 401. Every endpoint
  returns 401 without a valid token.
- The first request from a new token subject creates the `users` row (keycloak_id, email,
  display_name), safely under concurrent first requests. Controllers receive the local user id.
- Flyway migration `V1` creates users, categories and transactions: amounts are `NUMERIC(12,2)` and
  must be above zero. A composite foreign key means a transaction can only reference its own user's
  category. The tables live in their own `app` schema, because Supabase publishes `public` through
  its REST API.
- Spring Data JDBC instead of JPA: entities are records, the SQL is explicit, and there is no
  `ddl-auto`.
- Endpoints:
  - CRUD for `/api/categories` and `/api/transactions`; the transaction list filters on `from` and
    `to` (both inclusive) and `categoryId`.
  - `GET /api/dashboard/summary`, computed with SQL aggregates in a single snapshot. Balance is
    all-time; the other figures cover the requested range.
- Error rules: another user's row returns 404; another user's category returns 400; deleting a
  category that still has transactions returns 409; an amount with more than two decimals returns
  400 and is not rounded.

  at UTC+14 to catch dates shifting.
- Four planted bugs were all caught: a half-open date range, a floating-point sum, zero without two
  decimals, and a missing user filter.

**Open**

- Email and display name are captured on first sight only.
