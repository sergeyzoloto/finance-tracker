# Change Log

Newest first, one entry per completed task, each with the commit it landed in. The earlier
multi-service version of the project (2024–2025) was removed in `011537c` ("from scratch").

## 2026-09-25 · REST API for the double-entry ledger

Not committed yet.

**Changes**
- The API serves the ledger of ADR 0001: accounts, categories, counterparties, entries (paginated,
  filtered, with optimistic locking), reports, the Excel import as a multipart upload, and
  settings. The README lists every endpoint; springdoc describes them at `GET /api/openapi`.
- An entry's body is a domain command; its `kind` picks the command record through a Jackson
  mix-in. Amounts are JSON strings both ways.
- Errors are RFC 7807 problem details from one `@RestControllerAdvice`: 400 lists the invalid
  fields, 404 covers other users' objects, 409 a stale version or a conflicting change, 422 the
  ledger rules an entry breaks.
- A user's first request for data gives them settings (EUR) and a generic starter ledger from
  `seed/starter-ledger.json`, once, even for parallel first requests. OPENING_BALANCE and
  FX_EXCHANGE are system accounts, which can't be renamed or archived.
- The user id is the token's `sub`, resolved in `CurrentUserResolver` and passed to services.
  Tokens without a `sub` get 401.
- V1's API (categories, transactions, dashboard) is removed: `/api/categories` now serves the
  ledger's categories. V1's tables stay.

**Verified**
- 177 backend tests (`./mvnw -B verify`), 34 of them new, with MockMvc and spring-security-test's
  `jwt()`: 404 across users, reports without other users' data, 422 for an unbalanced manual entry,
  409 for a stale version, pagination and every filter, and the starter ledger seeded once under
  eight parallel first requests.

**Open**
- The frontend still calls V1's endpoints and has to be ported to the new API.
- No live run against the dev Keycloak or Supabase; V2 and V3 still aren't applied there.

## 2026-09-22 · Login moved to the shared auth server (realm `myapps`)

Not committed yet. Auth server repository: branch `finance-tracker-client`, commit `ebe48ee` (not pushed).

**Changes**
- Users sign in through the shared Keycloak, realm `myapps`, as client `finance-tracker`. The
  bundled Keycloak service, `infra/` (realm file and reuse guide) and Google/GitHub sign-in are
  gone, together with their `.env` variables. The details are in `docs/auth.md`.
- The backend is now the browser's backend-for-frontend. It runs the authorization code flow with
  PKCE as a confidential client, and keeps the tokens in its session. The browser gets only an
  `HttpOnly; Secure; SameSite=Lax` cookie.
- Every API request is authorized by an access token: the session's token, refreshed when it has
  under a minute left, or a bearer token from a service.
  - A token must have a valid signature, `iss`, `exp`/`nbf` (60 s skew) and `aud` containing
    `finance-tracker`, otherwise 401.
  - It must hold the client role `user`, otherwise 403. Realm roles and other clients' roles
    grant nothing.
  - Only members get a `users` row.
- Keycloak is contacted lazily. The app starts while Keycloak is down: the API answers 401, not
  500, and a login lands on `/?login=failed`. Both recover on their own.
- Writes from the browser need the CSRF token (cookie plus `X-XSRF-TOKEN` header). *Log out* ends
  the Keycloak session too, through the end-session endpoint.
- Frontend:
  - keycloak-js removed; the app asks `GET /api/me` who is signed in.
  - Non-members see "no access" with *Sign out*.
  - A 401 right after a login shows a message instead of looping.
- Local development: `docker-compose.local.yml`, enabled through `COMPOSE_FILE` in `.env`, puts
  the backend (8081) and nginx (3000) on the host network, next to the auth server's Keycloak on
  8080. nginx's config became a template for that. Vite serves on 5173.
- Auth server repository:
  - The client, its `user`/`admin` roles and `testuser`'s role in `realm-export.json`.
  - The production client in `realm-prod.json`, replacing the three example clients.
  - In both files, an audience mapper: Keycloak leaves the requesting client out of `aud`.
    Without the mapper, the app's own tokens would fail the `aud` check.

**Verified**
- 31 backend tests against a `FakeKeycloak` (no live Keycloak). Five planted bugs were each caught:
  no `aud` check, realm roles mapped, no PKCE, 500 during an outage, and no refresh margin.
- Against the auth server's dev Keycloak:
  - A `testuser` token got 200; a `shop-api` client-credentials token got 401.
  - A scripted Chrome session worked through nginx (3000) and through Vite (5173): a deep link to
    the login page and back, a write through the UI, a reload, and a logout that also ended the
    Keycloak session. No token was in browser storage.
  - A non-member was shown "no access" and got no `users` row.
  - A session was still open 255 s after login, when the token had under a minute left: the
    backend refreshed it (the Keycloak session's `lastAccess` moved), and calls kept working after
    the first token expired.
  - A backend started with Keycloak unreachable answered 401.
- The live runs found two bugs, both fixed:
  - The loop guard treated an abandoned login as a completed one. It now relies on `/?login=done`.
  - Vite's proxy shorthand rewrote the `Host` header, so the callback URL pointed at the backend.

**Open**
- The production steps in the auth server's admin console, and the production deployment itself.
- Still no Supabase credentials: the stack runs used a stand-in Postgres.

## 2026-09-22 · Integration pass: full walkthrough, restart resilience, reuse guide

Commit `e1cb35d`

Walked the whole loop in a scripted Chrome session against the real stack: Keycloak, the backend,
and the frontend served by nginx. Two parts ran on stand-ins. Postgres was a local stand-in, because
no Supabase credentials are configured. Google and GitHub sign-in used two temporary OpenID Connect
providers going through the same Keycloak broker path: no OAuth apps are registered yet, and a real
sign-in needs a person's own accounts. None of the stand-ins are in the repo.

**Results**
- Signing in through the two providers created two separate Keycloak users and two backend `users`
  rows, owning 5/8 and 2/2 categories and transactions. The second user saw none of the first
  user's data, even with categories of the same name.
- Dashboard totals matched a hand calculation to the cent. First user: balance 5,260.96; this
  month's income 3,650.50 and expenses 1,359.54; by category, Rent 1,200.00, Food 109.55 and
  Transport 49.99. Second user: balance 1,249.75; income 2,000.00 and expenses 750.25; Rent 750.25.
- Killing and restarting the backend mid-session: a message appeared within 0.1 s, the open screen
  recovered by itself 5.8 s after the restart, and the user was never sent back to Keycloak.

**Fixed**
- `frontend/nginx.conf`: nginx looked up `backend` once at startup. After the backend container was
  recreated with a new IP, every API call returned 502 until the frontend container was restarted.
  Right after a kill, requests also hung for up to 60 s. It now looks up `backend` through Docker's
  DNS on each request (`resolver 127.0.0.11`), with a 5 s connect timeout.
- `frontend/src/api.ts`: a 502, 503 or 504 shows "The server is unavailable right now…", and the
  screen's data reloads every 3 s until the backend answers. Writes are never retried automatically.

**Added**
- `infra/README.md`: step-by-step guide to reusing the Keycloak service and realm file in another
  project. A dry run in a scratch project ("acme") followed it literally: a two-line rename, a 42 s
  first start, a matching issuer, a PKCE login through the renamed client, correct provider
  callback URLs, and "Import skipped" on restart.
- Documented Keycloak behaviour, tested with the mock providers. The same email arriving through
  Google and GitHub gets "Account already exists… Add to existing account", so it becomes one user.
  A provider that sends no name gets a first-and-last-name form on first sign-in.

**Open**
- Register the Google and GitHub OAuth apps (`infra/keycloak/README.md`), then sign in with real
  accounts.
- Add the Supabase connection details to `.env`, and run `CREATE SCHEMA IF NOT EXISTS keycloak;`
  in Supabase.

## 2026-09-22 · Frontend: Keycloak login and the three screens

Commit `8b21e61`

**Changes**
- Login uses keycloak-js 26.2 with Authorization Code + PKCE (S256) on client `finance-frontend`,
  in `login-required` mode. There is no login form of our own: an unauthenticated visit goes to
  Keycloak and comes back to the requested page.
- Tokens are kept in memory only. After a page reload, the Keycloak session restores them without
  asking for the password. keycloak-js only puts short-lived redirect state (state, nonce, PKCE
  verifier) in `localStorage`, and removes it when Keycloak redirects back.
- `frontend/src/api.ts` attaches the Bearer token to every call, and refreshes it first if it
  expires within 30 s. On a 401 it forces a refresh and retries once.
  - If the Keycloak session is gone, keycloak-js sends the browser to the login page.
  - If the backend rejects even a freshly refreshed token, the app shows "The server did not accept
    your session." instead of redirecting, which would loop.
- Screens, using react-router 8:
  - Dashboard: all-time balance, this month's income and expenses, and spending by category.
  - Transactions: add, edit and delete, filtered by date range (default: current month) and category.
  - Categories: add, edit and delete, each marked income or expense. Deleting one that still has
    transactions shows the API's reason.
- The Keycloak URL is baked in at build time from `KEYCLOAK_URL` (the `VITE_KEYCLOAK_URL` build
  argument). The realm and client ID are constants in `frontend/src/auth.ts`.

**Verified** in a 19-check scripted browser run against the real stack, on both the nginx build and
the Vite dev override, stable over repeated runs:
- the PKCE redirect, no tokens in storage, and silent restore on reload
- add, edit and delete on every screen, and both filters
- exact dashboard figures
- 401 → refresh → retry, no redirect loop
- logout, and a session ended on the Keycloak side

A double redirect when the session expires was found and fixed during these runs.

**Notes**
- After a dependency change, start dev mode with `-V` so the container's `node_modules` is refreshed.
- The browser test script is not in the repo.

## 2026-09-22 · Backend: resource server, domain model, REST API

Commit `81f9779`

**Changes**
- Stateless OAuth2 resource server: it checks the token's issuer and signature using the realm's
  JWK Set URI. There are no sessions and no login page. CSRF protection is off, since only bearer
  tokens are used; with it on, a write without a token got 403 instead of 401. Every endpoint
  returns 401 without a valid token.
- The first request from a new token subject creates the `users` row (keycloak_id, email,
  display_name), safely under concurrent first requests. Controllers receive the local user id.
- Flyway migration `V1` creates users, categories and transactions: amounts are `NUMERIC(12,2)` and
  must be above zero. A composite foreign key means a transaction can only reference its own user's
  category. The tables live in their own `app` schema, because Supabase publishes `public` through
  its REST API.
- Spring Data JDBC instead of JPA: entities are records, the SQL is explicit, and there is no
  `ddl-auto`.
- Endpoints:
  - CRUD for `/api/categories` and `/api/transactions`; the transaction list filters on `from` and
    `to` (both inclusive) and `categoryId`.
  - `GET /api/dashboard/summary`, computed with SQL aggregates in a single snapshot. Balance is
    all-time; the other figures cover the requested range.
- Error rules: another user's row returns 404; another user's category returns 400; deleting a
  category that still has transactions returns 409; an amount with more than two decimals returns
  400 and is not rounded.

**Verified**
- 14 integration tests on Postgres 17 (Testcontainers), with real RS256 tokens. The test JVM runs
  at UTC+14 to catch dates shifting.
- Four planted bugs were all caught: a half-open date range, a floating-point sum, zero without two
  decimals, and a missing user filter.
- End to end with a real Keycloak token through nginx.

**Open**
- The transaction list has no pagination.
- Email and display name are captured on first sight only.
- The recommended audience (`aud`) check has not been added.

## 2026-09-22 · Database moved to Supabase Postgres

Commit `16727b7` (committed together with the scaffold)

**Changes**
- Removed the local `postgres` service, its volume and its init script. Keycloak and the backend
  connect to Supabase through the Session Pooler, using `SUPABASE_JDBC_URL`, `SUPABASE_DB_USER` and
  `SUPABASE_DB_PASSWORD`.
- Keycloak uses its own schema, `keycloak` (`KC_DB_SCHEMA`). It has to be created once before the
  first start, because Keycloak exits instead of creating it.
- The Keycloak health check's `start_period` is 10 minutes: the first boot against a database 30 ms
  away took 206 s.
- Both connection pools are capped at 5, because they share Supabase's session-mode limit.
- No app migrations needed re-running: the old app database had 0 tables. Keycloak re-applies its
  own schema changes on first start.

**Verified** against a stand-in Postgres, because no Supabase credentials were available: only
three containers start, Keycloak creates its tables in the `keycloak` schema, and the backend
connects. Not yet verified against Supabase itself.
