## 2026-09-28 · One token refresh per session, late login callback (D3a)

Commit `385cd2a`; the deploy's records: `5711645`.

**Changes**
- `SessionAccessTokenFilter`: one request of a session refreshes the access token at a time, which
  fixes the bug D3 found: parallel requests each refreshed an expiring token with the same refresh
  token, Keycloak refused the second with "Maximum allowed refresh token reuse exceeded", and the
  api ended the session.
  - A request whose token expires within the minute takes a `ReentrantLock` kept in the session,
    reads the session's authorized client again under it, and refreshes only if that token is
    still expiring. Otherwise it uses the token that the request before it got.
  - A refused refresh (`invalid_grant`) ends the session only while the refused refresh token is
    still the session's; tokens stored meanwhile by a sign-in in the same session stay. The
    manager's default failure handler, which removed the stored client on `invalid_grant`, is
    replaced by a no-op, so the filter decides alone. The end of a session is logged:
    `Keycloak refused to refresh the session's access token (…), so the session ends`.
  - The lock is in the JVM, which assumes the single api instance; the Javadoc and
    `docs/auth.md` say so.
  - Found on the way: Keycloak 26 (`TokenManager.validateTokenReuseForRefresh`) also detaches the
    client session when a refresh token is reused. The token the first refresh brought would then
    fail at its own refresh, so avoiding the second use matters, not only tolerating its error.
- `SecurityConfig`: a callback that fails with `authorization_request_not_found` in a session that
  already holds tokens goes to `/?login=done`, like a successful login, and logs
  `A late callback of a finished sign-in`. Otherwise the login-failed notice stays. The task said
  to redirect to `/`. `/?login=done` also lands on `/`, and when the browser dropped the first
  callback's response, the frontend reopens the page the user was on.
- Tests:
  - `FakeKeycloak` models Keycloak's client session: one valid refresh token per sign-in, a reuse
    refused with "Maximum allowed refresh token reuse exceeded" that also detaches the client
    session, and refreshes counted as granted and refused (`refreshCount`,
    `refusedRefreshCount`). It answers requests in parallel (virtual threads), can delay a
    subject's refreshes, and can give refreshed access tokens another lifetime than the first.
    It did already refuse a used refresh token, with another message; no test had sent parallel
    requests.
  - `BrowserLoginTests`: `parallelRequestsWithAnExpiredAccessTokenKeepTheSession` and
    `parallelRequestsRefreshTheAccessTokenOnce` (6 requests at once, refreshes delayed 300 ms),
    `aLateSecondCallbackOfAFinishedLoginLandsInTheApp`, and
    `aCallbackWithoutAnAuthorizationRequestFailsInASessionThatIsNotSignedIn`. Sessions are a
    `MockHttpSession` with synchronized attributes, as parallel requests share Tomcat's.
  - `security/SessionAccessTokenFilterTests`, with a stub refresher: a refusal ends the session
    while the refused token is the session's, and keeps it when a sign-in replaced the token.
- Docs: `docs/auth.md` (refresh, the lock, one instance, the late callback, the tests), the
  runbook's troubleshooting rows for the refresh bug (fixed) and `authorization_request_not_found`,
  step 8's note on the registration tab, and CLAUDE.md's project map.
- Deployed to production with the runbook's "Update the app", from `9287f0e` (Change log: D3a's
  commit), after the owner pushed and CI was green. Nothing else on the server changed; the realm
  and the auth repository are untouched (Keycloak was only read with `automation-cli`).
- After the deploy: a row in the runbook's "Deployed revisions". "Update the app" now says that

- The first request from a new token subject creates the `users` row (keycloak_id, email,
  display_name), safely under concurrent first requests. Controllers receive the local user id.
- Flyway migration `V1` creates users, categories and transactions: amounts are `NUMERIC(12,2)` and
  must be above zero. A composite foreign key means a transaction can only reference its own user's
  category. The tables live in their own `app` schema, because Supabase publishes `public` through
  its REST API.
- Spring Data JDBC instead of JPA: entities are records, the SQL is explicit, and there is no
  `ddl-auto`.
- Endpoints:
  - CRUD for `/api/categories` and `/api/transactions`; the transaction list filters on `from` and
    `to` (both inclusive) and `categoryId`.
  - `GET /api/dashboard/summary`, computed with SQL aggregates in a single snapshot. Balance is
    all-time; the other figures cover the requested range.
- Error rules: another user's row returns 404; another user's category returns 400; deleting a
  category that still has transactions returns 409; an amount with more than two decimals returns
  400 and is not rounded.

**Verified**
- 14 integration tests on Postgres 17 (Testcontainers), with real RS256 tokens. The test JVM runs
  at UTC+14 to catch dates shifting.
- Four planted bugs were all caught: a half-open date range, a floating-point sum, zero without two
  decimals, and a missing user filter.
- End to end with a real Keycloak token through nginx.

**Open**
- The transaction list has no pagination.
- Email and display name are captured on first sight only.
- The recommended audience (`aud`) check has not been added.

## 2026-09-22 · Database moved to Supabase Postgres

- Removed the local `postgres` service, its volume and its init script. Keycloak and the backend
