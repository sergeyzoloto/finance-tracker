## 2026-09-26 · Reports in the base currency and exchange rates

Commit `2e08797`. Backfilled on 2026-09-26 from the commit's diff.

**Changes**
- ADR 0002 (`docs/adr/0002-exchange-rates.md`):
  - Rates come from the ECB, shared by all users, and from each user's own manual rates.
  - Every rate is stored as units of a currency per 1 EUR, and cross rates go through the euro.
  - An amount on day D uses the latest rate on or before D, with no age limit.
  - A figure without a rate is missing, never 0.
  - FX results are computed on each call, never posted.
- `V4__exchange_rate_sources.sql`: `exchange_rate.user_id`, NULL for the ECB's rates and the sub
  for a manual one. The source is ECB or MANUAL, `base_currency` must be EUR, and a unique key on
  currency, day and user replaces the primary key.
- `ledger/rates/`:
  - `EcbClient` reads the ECB's daily XML (without DTDs) and its history ZIP.
  - `EcbRateLoader` stores the rates. It reads the history on the first load and whenever a weekday
    is missing.
  - `EcbSchedule` runs it at startup and at 16:30 and 18:30 Europe/Berlin on weekdays.
    `ECB_RATES_ENABLED=false` turns it off; it is off in tests and in the `import` profile.
  - `RateBook` picks the rate for a day. On the same day, the user's manual rate beats the ECB's.
- Balances, net worth and cash flow take `currency=BASE`. A second handler on the same path returns
  the report in the user's base currency (`Converted*` records).
  - A figure is null, with `missingRates`, if any of its amounts lacks a rate. It is rounded HALF_UP
    to 4 decimals once.
  - Net worth adds `unrealizedRevaluation` and `realizedExchangeResult`, both positive for a gain.
    Cash flow has both per month.
  - Any other value of `currency` is a 400.
- Rates API:
  - `/api/rates`: the latest rate per currency, and the days on which the user's postings lack a
    rate.
  - `/api/rates/manual`: list, add one rate, delete.
  - `/api/rates/manual/csv`: an upload with the columns date,base,quote,rate, saved all or nothing.
    A 422 lists the bad rows.
  - A manual rate needs EUR on one side. One given as EUR per unit is inverted to 8 decimals.
- Frontend:
  - A Rates page (`/rates`): the latest rates, the days without a rate, a form for one rate as
    "1 EUR = …", the CSV upload, and the user's own rates with delete.
  - The dashboard's `currency=base` view shows net worth, balances and cash flow in the base
    currency, with the exchange results as lines after the net.
  - A figure without a rate reads "rate missing", and so does every sum it is part of. The rates
    used are shown with their dates, and rates more than 7 days old are flagged.
  - `formatMoney(..., { rounded: true })` shows converted amounts with the currency's usual
    decimals.

**Verified**
- Nothing recorded in the commit. It adds 28 backend tests:
  - new classes: `RateBookTests` (5), `EcbClientTests` (4), `EcbRateLoaderTests` (5, against a local
    stand-in for the ECB), `BaseCurrencyReportTests` (6) and `RateApiTests` (5);
  - one more in `LedgerSchemaTests` and two in `ReportApiTests`.
- `ApiTests` adds the new endpoints to its 401 list and its OpenAPI paths.
- Frontend: 8 new tests of the base currency in `dashboard.test.ts` (6) and `CashFlowTable.test.tsx`
  (2). `money.test.ts` gains checks of typed rates (8 cases), rate formatting, and rounded converted
  amounts.

**Open**
- The base currency (EUR for every new user) can be changed only through `PUT /api/settings`; no
  screen has it.
- RUB after 2022-03-01 is converted at the ECB's last RUB rate until manual rates exist, as ADR 0002
  says.
- V4 isn't applied anywhere yet.

## 2026-09-25 · Importer for the Excel ledger

Commit `95ac98e`. Backfilled on 2026-09-26 from the commit's diff.

**Changes**
- `ledger/importer/` imports the owner's Excel ledger, exported as CSV, for one user, in this
  order:
  - accounts and categories, created or updated by the code in their `Line` column;
  - one entry per journal row;
  - the optional opening balances (columns line, currency, amount, date), one entry per date
    against `OPENING_BALANCE`.
- `EntryMapper` turns a row into postings, in plain Java:
  - The debit account gets +Sum and the credit account −Sum. The sign of Sum decides the direction.
  - If the two sides' currencies differ, the row becomes an exchange through `FX_EXCHANGE`.
  - The category goes on the `UNALLOCATED` posting, and the borrower (`LOAN_CA`) becomes the
    counterparty on `LOANS_ASSET`.
  - A Family row keeps the workbook's own split: the family's part is minus `FAMILY_EXP` and goes
    to `FAMILY_DEBT`. A warning names rows where the workbook's own part differs by a cent.
  - Entries are written through `EntryService`, so `LedgerValidator` checks them.
- The open points of ADR 0001:
  - FX-gain rows with Sum 0 are skipped. Those with a Sum are imported as income and listed for
    review.
  - A row with shared income (`FAMILY_INC`) is an error.
  - A loan row without a borrower gets the counterparty "Unassigned" and a warning.
- A run is one transaction, with a savepoint per row. A dry run always rolls back, and a commit
  rolls back if any row has an error.
- A row's `external_ref` is `xls:`, the SHA-256 of its business columns, and its occurrence among
  identical rows. A row the user already has is skipped, so running the import again is safe.
- `ImportRunner` is the command line, under the Spring profile `import`, with no web server.
  - `SecurityConfig` and `CurrentUserConverter` now load only in a web application.
  - It writes the `ImportReport` as Markdown next to the transactions file, and exits with 0, 1
    (arguments or files) or 2 (row errors, nothing saved).
  - CLAUDE.md shows the command.
- `EntryService.createImported` also records the import batch and the `external_ref`. New library:
  Commons CSV 1.14.1.
- `src/test/resources/import/` is a synthetic workbook with invented names.

**Verified**
- Nothing recorded in the commit. It adds 31 backend tests:
  - without a database: `ExcelValuesTests` (5), `WorkbookTests` (7) and `EntryMapperTests` (8);
  - against the database: `ImportServiceTests` (8: a dry run and a commit with a bad row save
    nothing, a second run skips what the first imported) and `ImportRunnerTests` (3: the report
    file and the exit codes).

**Open**
- The importer runs only from the command line. The commit message leaves a REST endpoint for
  later.
- V2 and V3 aren't applied to Supabase, so CLAUDE.md points the importer at a throwaway
  PostgreSQL.

## 2026-09-25 · Ledger schema and integrity triggers

Commit `5fefb15`. Backfilled on 2026-09-26 from the commit's diff.

**Changes**
- `V2__double_entry_ledger.sql` creates the ledger of ADR 0001 next to V1's tables.
  - Tables: `account`, `category`, `counterparty`, `journal_entry`, `posting`, `import_batch`,
    `exchange_rate` (shared by all users) and `user_settings`.
  - Owned rows are keyed by `user_id TEXT`, the Keycloak `sub`, and don't reference `users`.
- Amounts are `NUMERIC(19,4)` and never zero, and a currency is three capital letters.
- Accounts, categories and counterparties have `archived_at`, and postings refer to them with
  `ON DELETE RESTRICT`.
- `journal_entry` has a `version` for optimistic locking, and an `external_ref` for imports, unique
  per user.
- Triggers enforce what constraints can't:
  - At commit (deferred), every entry the transaction touched has at least 2 postings, which sum to
    zero per currency.
  - A posting's entry, account, category and counterparty belong to one user.
  - Only postings to EQUITY accounts have a category.
  - An account with `requires_counterparty` gets a counterparty on every posting.
  - An account can't change its type or `requires_counterparty` so that its postings break these
    rules.
  - `user_id` never changes.
- ADR 0001's status and CLAUDE.md name the new schema.

**Verified**
- Nothing recorded in the commit. It adds `LedgerSchemaTests`, 13 tests with plain JDBC on a freshly
  migrated database.
  - These entries fail at commit: an unbalanced one, one balanced in RUB but not in EUR, one without
    postings, and one that lost a posting. A balanced entry commits, and a moved posting checks both
    entries.
  - These fail: a category on an ASSET posting, a `LOANS_ASSET` posting without a counterparty, a
    reference to another user's row, an account change that would break its postings, and a change
    of owner.

**Open**
- No code uses the schema yet, and V2 isn't applied anywhere.
- V2 creates no rows. Nothing gives a user the system accounts `OPENING_BALANCE` and `FX_EXCHANGE`
  yet.
- V1's tables stay, although ADR 0001 says a new migration can drop them.

## 2026-09-22 · Login moved to the shared auth server (realm `myapps`)

Not committed yet. Auth server repository: branch `finance-tracker-client`, commit `ebe48ee` (not pushed).

**Changes**
- Users sign in through the shared Keycloak, realm `myapps`, as client `finance-tracker`. The
  bundled Keycloak service, `infra/` (realm file and reuse guide) and Google/GitHub sign-in are
  gone, together with their `.env` variables. The details are in `docs/auth.md`.
- The backend is now the browser's backend-for-frontend. It runs the authorization code flow with
  PKCE as a confidential client, and keeps the tokens in its session. The browser gets only an
  `HttpOnly; Secure; SameSite=Lax` cookie.
- Every API request is authorized by an access token: the session's token, refreshed when it has
  under a minute left, or a bearer token from a service.
  - A token must have a valid signature, `iss`, `exp`/`nbf` (60 s skew) and `aud` containing
    `finance-tracker`, otherwise 401.
  - It must hold the client role `user`, otherwise 403. Realm roles and other clients' roles
    grant nothing.

  - A 401 right after a login shows a message instead of looping.

  - The client, its `user`/`admin` roles and `testuser`'s role in `realm-export.json`.
  - The production client in `realm-prod.json`, replacing the three example clients.

## 2026-09-22 · Backend: resource server, domain model, REST API

Commit `81f9779`

**Changes**
- Stateless OAuth2 resource server: it checks the token's issuer and signature using the realm's
  JWK Set URI. There are no sessions and no login page. CSRF protection is off, since only bearer
  tokens are used; with it on, a write without a token got 403 instead of 401. Every endpoint
  returns 401 without a valid token.
- The first request from a new token subject creates the `users` row (keycloak_id, email,
  display_name), safely under concurrent first requests. Controllers receive the local user id.
- Flyway migration `V1` creates users, categories and transactions: amounts are `NUMERIC(12,2)` and
  must be above zero. A composite foreign key means a transaction can only reference its own user's
  category. The tables live in their own `app` schema, because Supabase publishes `public` through
  its REST API.
- Spring Data JDBC instead of JPA: entities are records, the SQL is explicit, and there is no
  `ddl-auto`.
- Endpoints:
  - CRUD for `/api/categories` and `/api/transactions`; the transaction list filters on `from` and
    `to` (both inclusive) and `categoryId`.
  - `GET /api/dashboard/summary`, computed with SQL aggregates in a single snapshot. Balance is
    all-time; the other figures cover the requested range.
- Error rules: another user's row returns 404; another user's category returns 400; deleting a
  category that still has transactions returns 409; an amount with more than two decimals returns
  400 and is not rounded.

**Verified**

  at UTC+14 to catch dates shifting.
- Four planted bugs were all caught: a half-open date range, a floating-point sum, zero without two
  decimals, and a missing user filter.
