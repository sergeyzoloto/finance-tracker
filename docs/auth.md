# Authentication

Finance Tracker keeps no login, password or user-management code of its own. Users sign in on the
login page of the shared Keycloak server (the auth server repository), realm `myapps`, which every
`myapps` project uses with single sign-on. This project is the client `finance-tracker` in that realm.

- **Browsers:** the Spring backend is the browser's backend-for-frontend (BFF). It runs the
  authorization code flow with PKCE (S256) as a confidential client and keeps the tokens in its
  server-side session. The browser only gets an `HttpOnly; Secure; SameSite=Lax` session cookie.
  No token ever reaches the browser.
- **API:** every request under `/api` is authorized by an access token that the backend validates
  itself: the signature against the realm's cached keys, `iss`, `exp` and `nbf` (60 s clock skew),
  and `aud`. It then checks that the token holds this client's `user` role. A browser request uses
  the access token from its session; a service or `curl` sends `Authorization: Bearer <token>`.

## Issuer per environment

| Environment | Issuer (`KEYCLOAK_ISSUER_URL`)             | Keycloak                                                        |
| ----------- | ------------------------------------------ | --------------------------------------------------------------- |
| Development | `http://localhost:8080/realms/myapps`      | `docker compose up -d` in the auth server repo; admin console at `http://localhost:8080` (`admin` / `admin_dev_password`) |
| Production  | `https://auth.finance-nl.com/realms/myapps` | Already running; admin console only from allowlisted IPs, with OTP |

The issuer must equal the tokens' `iss` claim character for character. Endpoints (authorization,
token, keys, end-session) come from `<issuer>/.well-known/openid-configuration`. Nothing is
hardcoded, and nothing is fetched at startup (see [Keycloak down](#when-keycloak-is-down)).

## The client

`finance-tracker` is defined in the auth server repo: `realm-export.json` for dev and
`realm-prod.json` as the record of production.

| Setting | Development | Production |
| --- | --- | --- |
| Type | confidential, standard flow, PKCE S256 required | same |
| Secret | `finance-tracker-secret` | generated by Keycloak (*Clients → finance-tracker → Credentials*) |
| Redirect URIs | `http://localhost:3000/login/oauth2/code/keycloak`, `http://localhost:5173/login/oauth2/code/keycloak` | `https://app.finance-nl.com/login/oauth2/code/keycloak` |
| Post-logout redirect URIs | `http://localhost:3000/`, `http://localhost:5173/` | `https://app.finance-nl.com/` |
| Web origins | none (the browser never calls Keycloak with CORS) | none |
| Password grant | on, for `curl` tests only | off |
| Service account | off: this project calls no other `myapps` service | off |
| Mapper | audience `finance-tracker` added to the client's own access tokens | same |

The audience mapper matters. Keycloak lists a client in `aud` when the token carries that
client's roles, but leaves out the client that requested the token. Without the mapper, the API
would reject the tokens it gets through its own login.

## Roles and access (members only)

| Role | Kind | What it allows |
| --- | --- | --- |
| `user` | client role of `finance-tracker` | Using Finance Tracker: your own categories, transactions and dashboard. Required for every `/api` endpoint. |
| `admin` | client role of `finance-tracker` | Nothing yet; reserved for future admin features. Give admins `user` too. |
| `user` | realm role, held by every `myapps` user | Nothing here. Not mapped (see below). |
| any role of another client | e.g. `shop-api`'s `admin` | Nothing here. |

An administrator grants access by assigning `finance-tracker` → `user` to each user
(*Users → user → Role mapping → Assign role → Filter by clients*). Without it:

- A user who signs in through the app gets **403**. The app then shows "Your account has no
  access to Finance Tracker" with a *Sign out* button.
- A token from another client or service without this client's roles has no `finance-tracker` in
  `aud`. It gets **401**. Example: `shop-api`'s client credentials.
- No `users` row is created. Rows (`app.users`) are keyed on the token's `sub`, the stable
  Keycloak user ID, and created on the first request of a member. Email and name are stored for
  display only. Passwords and roles are never stored.

## How a browser session works

1. The page calls `GET /api/me`. Without a session this returns 401. The app remembers the current
   page and sends the browser to `/oauth2/authorization/keycloak`.
2. The backend redirects to Keycloak with a PKCE challenge, `state` and `nonce`. The user signs in
   on Keycloak's page. There's no sign-up and no "forgot password": admins create users.
3. Keycloak redirects to `/login/oauth2/code/keycloak`. The backend exchanges the code, using the
   client secret and the PKCE verifier, and validates the ID token. It keeps the tokens in the
   session and sends the browser to `/?login=done`. The app reopens the remembered page.
4. On each API call, the backend takes the session's access token. It refreshes the token first
   if it expires within 60 s, then validates it like any bearer token.
   - If Keycloak refuses the refresh, the Keycloak session is over: logged out elsewhere, expired,
     or the user was disabled. The backend then ends its own session and answers 401, and the app
     goes back to the login page.
5. Writes need the CSRF token. The backend sets a readable `XSRF-TOKEN` cookie, and the app echoes
   it in the `X-XSRF-TOKEN` header, or in the `_csrf` form field for logout. Bearer-token and
   session-less requests are exempt, since only the session cookie is sent automatically.
6. *Log out* posts to `/logout`. The backend ends its session and redirects to Keycloak's
   end-session endpoint with `id_token_hint` and `post_logout_redirect_uri`, which ends the
   Keycloak session too.

Sessions live in the backend's memory and end after 30 minutes idle, or on a backend restart.
After a restart, the next request goes through the login again. If the Keycloak session is still
alive (30 min idle, 10 h max), that is a quick redirect with no password prompt.

## When Keycloak is down

- The backend starts anyway. Discovery and signing keys load on the first request that needs them,
  and a failed load is retried on the next.
- Tokens that can be checked with already-cached keys keep working until they expire (5 minutes).
  After that, requests get 401, not 500.
- New logins and refreshes fail. A login attempt lands on `/?login=failed`, and the app offers
  *Try again*.

## Configuration

| Variable | Used by | Dev value (`.env.example`) | Production |
| --- | --- | --- | --- |
| `KEYCLOAK_ISSUER_URL` | backend | `http://localhost:8080/realms/myapps` | `https://auth.finance-nl.com/realms/myapps` |
| `KEYCLOAK_CLIENT_ID` | backend | `finance-tracker` | `finance-tracker` |
| `KEYCLOAK_CLIENT_SECRET` | backend | `finance-tracker-secret` | from Keycloak's *Credentials* tab, kept in the secret store, never in git |
| `COMPOSE_FILE` | Docker Compose | `docker-compose.yml:docker-compose.local.yml` | delete the line |
| `BACKEND_PORT` | local setup | `8081` | not used |
| `FRONTEND_PORT` | Docker Compose | `3000` | as needed |

In `backend/src/main/resources/application.yml` these become `app.keycloak.*`, and the resource
server's `issuer-uri` and `audiences`. The frontend has no auth configuration; it only uses
relative paths.

Production also needs:
- **HTTPS at `https://app.finance-nl.com`:** the session and CSRF cookies are `Secure`.
- **A TLS proxy that sends `X-Forwarded-Proto: https`:** nginx passes it on, so the backend
  builds `https://` redirect URIs.
- **One backend instance:** sessions are in memory. More than one would need sticky sessions or a
  shared session store.

## Running against the dev stack

1. Start the auth server: `docker compose up -d` in the auth server repository.
   - Its realm must contain the `finance-tracker` client. If your dev database predates the client,
     add it without wiping data, from the auth server repo:
     ```bash
     KC=http://localhost:8080
     ADM=$(curl -s -X POST $KC/realms/master/protocol/openid-connect/token -d grant_type=password \
       -d client_id=admin-cli -d username=admin -d password=admin_dev_password | jq -r .access_token)
     jq '{ifResourceExists: "SKIP", clients: [.clients[] | select(.clientId == "finance-tracker")],
          roles: {client: {"finance-tracker": .roles.client["finance-tracker"]}}}' realm-export.json |
       curl -s -X POST -H "Authorization: Bearer $ADM" -H 'Content-Type: application/json' \
         --data @- $KC/admin/realms/myapps/partialImport
     ```
     Then assign `finance-tracker` → `user` to `testuser` in the admin console.
   - The other option, `docker compose down -v && docker compose up -d`, re-imports the realm but
     deletes all dev data.
2. In this repo: `cp .env.example .env`, fill in the Supabase values, then `docker compose up --build`.
   - `COMPOSE_FILE` in `.env` adds `docker-compose.local.yml`, which puts the backend (port 8081)
     and nginx (port 3000) on the host network. Tokens name `localhost:8080` as their issuer, and
     the backend must reach Keycloak at that same address.
3. Open `http://localhost:3000` and sign in as `testuser` / `test1234`.

Hot reload: `docker compose -f docker-compose.yml -f docker-compose.local.yml -f docker-compose.dev.yml up --build`,
then open `http://localhost:5173`.

## A dev token for curl

The password grant is enabled for this client in dev only:

```bash
TOKEN=$(curl -s -X POST http://localhost:8080/realms/myapps/protocol/openid-connect/token \
  -d grant_type=password -d client_id=finance-tracker -d client_secret=finance-tracker-secret \
  -d username=testuser -d password=test1234 | jq -r .access_token)
curl -i -H "Authorization: Bearer $TOKEN" http://localhost:3000/api/me          # 200 {"name":"Test User"}
```

A token from another client without this client's roles is rejected:

```bash
SHOP=$(curl -s -X POST http://localhost:8080/realms/myapps/protocol/openid-connect/token \
  -d grant_type=client_credentials -d client_id=shop-api -d client_secret=shop-api-secret | jq -r .access_token)
curl -i -H "Authorization: Bearer $SHOP" http://localhost:3000/api/me           # 401, "The aud claim is not valid"
```

## Tests

The backend tests need Docker (Testcontainers Postgres), but no Keycloak. `FakeKeycloak` serves
discovery, keys and a token endpoint that checks the client secret and the PKCE verifier. It signs
RS256 tokens with a key generated per run.

- `AccessTokenTests`: 401 and 403 rules for bearer tokens.
- `BrowserLoginTests`: the code flow, refresh, CSRF and logout.
- `KeycloakOutageTests`: start and recovery while Keycloak is down.
- `security/RoleMappingTests`: the role mapping.

## Deviations from the auth server's reference integration

- **Realm roles aren't mapped.** The reference `SecurityConfig` maps them, so its `ROLE_USER`
  would admit every `myapps` user. Here only `finance-tracker` client roles become authorities.
- **`aud` must name `finance-tracker`.** The reference skips the audience check.
- **The client has an audience mapper for its own tokens** (see [The client](#the-client)).
- **Browser login via the backend (BFF), not a bearer-only API.** It adds
  `spring-boot-starter-oauth2-client`, a lazily loaded client registration, and session-based CSRF
  protection.

## Known limits

- **`aud` proves membership, not intent.** With Keycloak's default *Full scope allowed*, a token
  that any `myapps` client requests for a member also carries `finance-tracker` in `aud`, so this
  API accepts it. Example: `shop-api` requesting a token for `testuser`. Restricting that is a
  realm-wide change in the auth server.
- **Sign-out elsewhere is noticed within 5 minutes, not immediately.** An SSO logout in another
  `myapps` app ends this app's session at the next refresh. Back-channel logout isn't set up.
- **Google and GitHub sign-in are gone.** They belonged to the old per-project realm, and `myapps`
  has no identity providers.
